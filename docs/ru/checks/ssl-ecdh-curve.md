# `ssl_ecdh_curve` и постквантовый обмен ключами

_ID проверки Gixy: `ssl_ecdh_curve`_

С тех пор как OpenSSL 3.5 поставляет постквантовый гибрид `X25519MLKEM768`,
однострочная директива `ssl_ecdh_curve` может ошибаться тремя разными
способами:

| Находка | Серьёзность | Пример |
|---|---|---|
| Постквантовая группа без `?` | HIGH | `X25519MLKEM768:X25519:prime256v1` |
| Только классические группы | MEDIUM | `X25519:secp384r1:prime256v1` |
| Постквантовая группа в одном ярусе с классическими | LOW | `?X25519MLKEM768:X25519:prime256v1` |

Чистый вариант для nginx, собранного с OpenSSL 3.5+, — **не задавать
директиву вовсе**. Если список всё же нужен, вынесите гибрид в отдельный
верхний ярус:

```nginx
ssl_ecdh_curve ?X25519MLKEM768/X25519:prime256v1;
```

## HIGH: постквантовая группа, из-за которой nginx не запускается

nginx передаёт значение напрямую в OpenSSL:

```c
/* src/event/ngx_event_openssl.c */
if (SSL_CTX_set1_curves_list(ssl->ctx, &conf->ecdh_curve...) == 0) {
    ngx_ssl_error(NGX_LOG_EMERG, ssl->log, 0,
                  "SSL_CTX_set1_curves_list(\"%V\") failed", &conf->ecdh_curve);
    return NGX_ERROR;
}
```

Два свойства складываются неудачно:

1. **OpenSSL отвергает весь список**, если не знает хотя бы одно имя группы.
   Частичного принятия нет: `X25519MLKEM768:X25519:prime256v1` отклоняется
   целиком, хотя две группы из трёх поддерживаются везде.
2. **nginx пишет это на уровне `NGX_LOG_EMERG`** и возвращает ошибку, поэтому
   мастер-процесс не завершает конфигурацию. Это отказ запуска, а не откат на
   уровне соединения.

`X25519MLKEM768` и родственные группы появились в **OpenSSL 3.5**. Что
поставляют дистрибутивы (проверено в ноябре 2026):

| Дистрибутив | Системный OpenSSL | `X25519MLKEM768` |
|---|---|---|
| Debian 13 (trixie) | 3.5 | ✓ |
| RHEL / AlmaLinux / Rocky 9 (9.8) | 3.5 | ✓ |
| Debian 12 (bookworm) | 3.0 | ✗ nginx не запустится |
| Ubuntu 24.04 / 22.04 LTS | 3.0 | ✗ nginx не запустится |
| RHEL / AlmaLinux / Rocky 8 | 1.1.1 | ✗ nginx не запустится |

Значение имеет библиотека, с которой собран *nginx*, а не системная: проверьте
`nginx -V 2>&1 | grep "built with"`. [Пакеты NGINX от
GetPageSpeed](https://www.getpagespeed.com/repo-subscribe) собраны с OpenSSL 3.5
LTS на всех перечисленных платформах, включая те, где система даёт 3.0 и 1.1.1.

Предстандартные имена `X25519Kyber768Draft00` из старых сборок на BoringSSL и
руководств 2024 года ломаются так же.

### Префикс `?` и его собственное ограничение по версии

`?` велит OpenSSL пропустить незнакомое имя группы, а не отвергать весь список.
Он появился в **OpenSSL 3.3**: в OpenSSL 3.0 и 3.2 `?X25519MLKEM768` само по
себе нераспознаваемое имя и ломается точно так же. Разделитель ярусов `/`
требует OpenSSL 3.5. Поэтому:

- **OpenSSL 3.5+**: `?X25519MLKEM768/X25519:prime256v1` или без директивы.
- **OpenSSL 3.3 / 3.4**: ML-KEM нет. `?` не даст списку упасть, но
  договариваться о постквантовом обмене не с чем.
- **OpenSSL 3.0 / 3.2 / 1.1.1**: не указывайте постквантовые группы совсем.
  Не задавайте директиву или перечисляйте только классические кривые.

## MEDIUM: только классические группы

```nginx
# Совет по усилению из эпохи до ML-KEM. На OpenSSL 3.5+ он выключает постквант.
ssl_ecdh_curve X25519:secp384r1:prime256v1;
```

Явный список **заменяет** умолчание OpenSSL, а не дополняет его. В OpenSSL
3.5+, где умолчание начинается с `X25519MLKEM768`, список из одних классических
групп отказывает гибриду для всех клиентов, включая браузеры. `nginx -t`
проходит, в лог ничего не пишется, замок в браузере выглядит так же.

Безопасное на любой версии OpenSSL исправление — удалить директиву и положиться
на умолчание библиотеки. На OpenSSL 3.5+ можно вместо этого добавить
постквантовый ярус в начало: `?X25519MLKEM768/X25519:secp384r1:prime256v1`.

## LOW: постквантовая группа в одном ярусе с классическими

OpenSSL 3.5 читает список групп как **ярусы предпочтения**: `:` объединяет
группы в один ярус, `/` начинает следующий, более низкий. Внутри яруса сервер
берёт ту долю ключа (key share), которую клиент прислал первой; более сильную
группу он требует только между ярусами.

Клиент TLS 1.3 может предложить группу, не прислав для неё долю ключа. С
`?X25519MLKEM768:X25519:prime256v1` клиент, который предлагает гибрид, но
первой шлёт долю X25519, получит классический X25519. С
`?X25519MLKEM768/X25519:prime256v1` сервер вместо этого отвечает
HelloRetryRequest и просит долю гибрида — ценой одного лишнего обмена.

Измерено на nginx 1.30 с OpenSSL 3.5.9:

| Доли ключа клиента | `A:B` (один ярус) | `A/B` (два яруса) |
|---|---|---|
| гибрид, X25519 | `X25519MLKEM768` | `X25519MLKEM768` |
| X25519, гибрид | `X25519` | `X25519MLKEM768` |
| только X25519, гибрид предложен | `X25519` | `X25519MLKEM768` (HRR) |

Актуальные Chrome, Firefox, curl/OpenSSL 3.5, Go и Java присылают долю гибрида
и получают `X25519MLKEM768` при любой форме. Ярус важен для клиентов, которые
начинают с X25519, например для соединений Cloudflare с origin-серверами до
внедрения Automatic Key Exchange в 2026 году. Поэтому серьёзность — LOW.

## Что эта проверка не помечает

- Отсутствие `ssl_ecdh_curve` или `ssl_ecdh_curve auto;` (умолчание nginx).
- Списки на основе ключевого слова OpenSSL `DEFAULT`, например `DEFAULT:-X448`.
- Постквантовые группы с префиксом `?` в собственном верхнем ярусе.
